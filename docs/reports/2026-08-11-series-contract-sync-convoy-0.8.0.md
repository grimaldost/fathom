# The series arm against engine 0.8.0 — contract sync, and why the deciding measurement was not bought

- **Date:** 2026-08-11 (wave 2, branch `eval/wave-2`).
- **Two questions, answered separately.** (1) Does fathom's series arm still read the engine
  after the 0.8.0 release marked five entries **(consumer-affecting)**? (2) Can the deciding
  measurement for the series strategy — FATH-B17, which gates the engine's own CONV-B27 — be run
  inside this wave's budget?
- **Answers.** (1) Yes, after one minimal fix, now pinned by a regression test against fixtures
  generated by the engine's own writer. (2) **No** — and the blocker is not money.

---

## Part 1 — the contract sync

fathom drives the multi-PR engine as a scored arm and holds its own copy of the engine-agnostic
contract (`docs/specs/2026-07-03-series-engine-contract.md`). That makes an additive engine release
a contract-sync event *here*, which is exactly the case both backlogs warned about. Engine 0.8.0
added, all additively:

| 0.8.0 addition | Where it lands | fathom's series arm |
|---|---|---|
| `spawn_start` event (in-flight marker, no economy) | telemetry stream | **safe** — `_materialize_runs` filters on `event == "spawn_complete"`, so a started-but-uncompleted spawn contributes no economy row. Counting it would have doubled every arm's session count. |
| `effort`, `budget_cap_usd`, `budget_nearing`, `classification`, `output_tail` on `spawn_complete` | telemetry stream | **safe** — the named economy fields are unchanged, and `_event_to_record` keeps the whole event in `usage`, so the new fields reach a consumer rather than being dropped. |
| `spec_path` / `spec_sha256` on `run_start`; two new `series.toml` keys | telemetry + series file | **safe** — fathom authors its own series file and sets no pin, which the engine treats exactly as before the keys existed. |
| `run_abandoned` terminal event; `abandoned` joins the outcome vocabulary | telemetry stream | **BROKEN — fixed here.** See below. |
| `dead` as a run *state*; per-PR `in_flight` in the run envelope | `convoy status` / the run envelope | **not on this wire.** fathom reads the telemetry JSONL directly and never calls the status verb or parses the envelope, so neither reaches it. Worth stating plainly, because the wave brief expected the envelope to be the coupling surface and it is not. |

### The one real break

`_final_run_outcome` recognised only `run_complete`. A stream terminated by `run_abandoned` therefore
returned `None`, and `_classify` fell through to judging the trial on the engine's **exit code
alone**. A run whose driver was killed can leave a wrapper that exits 0, so an abandoned run would
have been scored a **COMPLETED task** — a fabricated success, in the strategy whose whole justification
is a gate that can reject "done".

The fix is three lines and takes the engine's own framing: `run_abandoned` carries no `outcome` field
(the engine's changelog is explicit that the writer "was not there"), so it is **mapped** to
`abandoned` rather than read, and `abandoned` classifies as INFRASTRUCTURE — outside the trial's own
work, excluded from the pass rate, re-runnable. `src/fathom/strategies/series.py`.

### How it is pinned

`tests/test_series_contract_convoy_080.py` (8 tests, stdlib-only) reads two committed fixtures under
`tests/fixtures/`. Both were generated by the **engine's own** `convoy.core.telemetry` dataclasses and
`to_json_line` at 0.8.0, so they cannot drift from the real writer through transcription error; the
test itself never imports the engine, so the stdlib-core invariant holds. Reverting the fix turns
`test_classified_infrastructure_not_completed` red.

### The live end-to-end evidence, which came for free

`fathom smoke` group 4 drives a real one-PR engine run with `claude` shadowed by a token-free shim,
and `scenarios/series.toml` resolves `[tools] repo = "../convoy"` to the **merged 0.8.0 worktree**. It
passed 8/8 this wave — *"2 engine claude spawn(s); permission-mode(s)=['default', 'default']"* — so the
engine still loads a series file fathom authored, still runs its pre-flight, and still spawns under
the pinned non-bypass permission mode. That check covers the authoring and spawning half; the
regression test above covers the reading half, which is the half that was broken.

## Part 2 — FATH-B17, the deciding measurement: planned, priced, NOT run

FATH-B17 asks for the engine arm against `ablation-v2`'s brownfield instrument **at the weak tier** —
the one configuration in the corpus where the bare arm actually fails, so an orchestration engine has
escapes to catch. The comparison set already exists in `ledger/ablation-v2.jsonl`:

| weak-tier arm | all-criteria pass |
|---|---|
| `haiku` (bare) | 3/8 |
| `haiku-gate` | 3/8 |
| `haiku-gate-sg` (strengthened gate) | ~~9/10~~ **VOID** |
| `haiku-gate-review` | 5/10 |
| `haiku-authoring` | 4/10 |
| `haiku-reprompt` | 4/8 |
| **`series` (the engine)** | **does not exist** |

> **CORRECTION (2026-08-28).** The `haiku-gate-sg` row above is **void** and must not be used as a
> comparator. Its type probe shipped as a literal placeholder path, so the probe never executed and
> the arm ran as its own control; its `config_hash` has no preimage, so the configuration is
> unattributable. This matters here specifically because the table is framed as the comparison set a
> future **paid** engine arm would be measured against -- FATH-B17 must not be priced against this
> number. The weak-tier bar is `haiku` 3/8 and `haiku-gate` 3/8; the strengthened-gate cell is empty
> until `haiku-gate-sg2` runs. See `docs/reports/2026-08-11-ablation-v2-series-arm-authoring.md`
> section 1.

### Why it was not run — the blocker is authoring risk and wall-clock, not dollars

`SeriesExecutor` reads `<task_dir>/series.toml` and copies a committed `prompts/` tree beside it. **The
`ablation-v2` bank has neither.** No bank in the tree does: the original series bank was retired and
its ledger archived. So the run is blocked on authoring a genuine multi-PR decomposition of the
`exprlang` feature — a dependency-ordered PR set with per-PR prompts and gate wiring.

That is not clerical work, and getting it wrong is the expensive failure. A weak decomposition
produces a poor engine result, the engine arm loses, and FATH-B36 retires the strategy, the contract
spec and a smoke group **on the strength of a decomposition this wave would have written in an hour**.
The outcome the decision wants and the outcome a badly-authored instrument produces are the same
outcome — the exact trap the gate-banks spec names, and the reason the ablation is worth doing
properly rather than cheaply.

| | |
|---|---|
| Matrix to fill the gap | 1 `series` arm × 1 task (`exprlang`) × n = 8, matching `haiku` / `haiku-gate` |
| Token cost | **low** — weak tier, and the engine's own spawns bill at haiku rates; the 2026-06-10 series bank ran ~4.6× tokens and 8 sessions/trial, which at haiku is roughly **$0.50–2.00/trial → $4–16 total** |
| Wall-clock | **the real cost**: `trial_timeout_s = 3600` per trial, up to **8 hours** for n = 8, sequential |
| Authoring | a multi-PR decomposition of `exprlang` + per-PR prompts + `series.toml`, none of which exists |
| Free preconditions already discharged | `fathom validate ablation-v2` (the bank is valid), `fathom smoke` group 4 (the engine boundary is live against 0.8.0), and the contract sync above |

**Recommendation, and it is a sequencing one.** The measurement is *cheap in money* and should
happen — but the decomposition is the instrument, so author it as its own deliverable and have it
reviewed before any spend, exactly as the gate-banks spec recommends for the mantis question set.
Until then, CONV-B27's ADR should say the residual claim is **unmeasured** and name FATH-B17 as what
would settle it, rather than reading as settled. That is the same instruction the engine's own
cross-review already gives itself.

**One correction to how FATH-B17 is currently framed.** It says "the bank, arms and oracle already
exist and the real cost is near zero under subscription auth". The bank and the oracle exist; the
**arm does not** — there is no series scenario for `ablation-v2` and no series template for
`exprlang`. The near-zero cost claim is right and is the least interesting part of the item.
